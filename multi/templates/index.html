Supervisor / Worker agents

A minimal teaching demo — watch a supervisor decompose a task, delegate to workers who each run their own loop, then merge the results.

Supervisor: thinks, plans, dispatches, collects, synthesises.

How it works

There are two concentric loops at play. Zoomed out, the supervisor manages a loop over the whole plan. Zoomed in, each worker runs its own little loop over a single sub-task.

The supervisor loop (divide & conquer)
① Thinks
read the task
→
② Plans
split into sub-tasks
→
③ Dispatches
one worker each
→
④ Collects
wait for all
→
⑤ Synthesises
one final answer

The supervisor never does the actual work. It is a manager: it breaks the job into pieces that don't depend on each other, hands each piece to a fresh worker, waits, and merges the reports back into a single answer.

The worker loop (ReAct, run by each worker)
Think
what do I need?
→
Act
call a tool
→
Observe
read the result
→
Repeat / Stop
final answer

ReAct = Reason + Act. Each worker repeatedly thinks about what to do, acts by calling one of its tools, and observes the result — until it has enough to stop and give its final answer. Its focus is narrow, so its system prompt and toolset are small and sharp.

Why supervisor-worker?

  • Parallelism — independent sub-tasks run at the same time, so big jobs finish faster than one agent grinding through everything.
  • Separation of concerns — each worker has one role and a tiny toolset, so it makes fewer mistakes than one agent doing everything.
  • Single point of assembly — only the supervisor talks to the user; workers just report up. That keeps the final answer coherent.
  • The cost — decomposition overhead, possible duplicate work, and a bottleneck: the supervisor can't synthesis until every worker has finished.
